## Выбранное направление: официальный API Директа

По официальной документации API поддерживает ЕПК, кампании, группы и объявления. Для ЕПК используются сервисы campaigns/adgroups/ads версии v501.
Это подходящий путь для точных изменений и последующего чтения сохранённых значений без работы с нестабильными элементами страницы.
**Подключение ещё не создано, авторизованных вызовов API аккаунта не было.** Не объявлять это уже работающей автоматизацией.

Проверка сети из рабочего окружения:
- Запрос campaigns.get без OAuth-токена к https://api.direct.yandex.com/json/v501/campaigns прошёл с проверкой HTTPS.
- Сервер ответил HTTP 200 и ошибкой API 8000 «OAuth-токен не указан».
- Это доказывает доступность API по сети, а не доступ к данным кампании или право их изменять.
- Секреты/переменные Яндекса в окружении не настроены.

Проверка аккаунта через браузер:

- Кампания 715775801 — рекламная кампания, не OAuth-приложение; не искать приложение с таким названием.

## Обязательные шаги подключения

1. Создать OAuth-приложение Яндекс ID для доступа к API/отладки. По текущей инструкции Direct: источник direct:api, а также passport:business для авторизации от имени организации в ID. Уточнить применимость последнего к фактическому личному аккаунту; не запрашивать почту/диск и иные лишние права.
2. В настройках API Директа пройти первоначальное соглашение владельцем и подать заявку на зарегистрированный ClientID с фактическими данными приложения. Уже созданная кампания удовлетворяет требованию наличия хотя бы одной кампании для открытия настроек.
3. Дождаться одобрения. Официальный срок рассмотрения — до семи дней; не обещать немедленное подключение.
4. Подключить OAuth владельца через штатную страницу Яндекса. Client secret и токен хранить только в закрытом хранилище/привязке секрета окружения, не в чате, публичных документах, коммитах или аргументах команд.
5. Проверить авторизованным campaigns.get только кампанию 715775801 и сопоставить имя/статус/состояние с кабинетом.
6. Затем подготовить клиент: сначала чтение и предварительный diff, изменения только разрешённой кампании, обработка ошибок/квот и повторное чтение результата. Повтор операций создания не должен порождать дубли.
7. Отдельно заблокировать в клиенте запуск, модерацию, возобновление, пополнение и увеличение лимитов до явного разрешения владельца. OAuth direct:api сам по себе даёт широкие возможности; внутренние ограничения клиента нужно реально реализовать и проверить, а не считать встроенными правами Яндекса.
8. Согласовать расходы с НДС/начислениями и период; первый этап до 1 000 ₽, общий тест до 3 000 ₽/7 дней не изменены. Сохранённые в черновике 1 550 ₽/31 день не разрешают расход.
9. Регулярное выполнение и ежедневные отчёты подключать отдельно, после известного запуска и проверки устойчивости доступа. API не означает круглосуточную работу ассистента без расписания.

**Каталог подключений.** Повторный поиск Yandex/Direct и браузерных интеграций не нашёл прямого подключения Яндекса или Browserbase. Из подходящих браузерных средств найден уже установленный TinyFish; нерелевантные плагины не устанавливались. Поиск не является полным каталогом всех внешних продуктов.

**Прямой Playwright/Chromium.** В текущем окружении установлены Python Playwright и Chromium. Python HTTPS-запросы работают через штатный прокси. Chromium остановился с ERR_CERT_AUTHORITY_INVALID даже после проверки штатных публичных CA; проверка HTTPS не отключалась. Пользовательский вход не выполнялся, cookies TinyFish не извлекались и не переносились, отладочный порт наружу не открывался. Тестовый браузер остановлен. Рабочей альтернативой этот вариант пока не считать. Сеанс окружения может меняться; файлы теста в /tmp не являются постоянным сервисом.
